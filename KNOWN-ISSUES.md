# Known issues

- **Pages have no `label`, but the AI service reads `block.label`.** A page is named by `title`. To keep that out-of-scope file compiling without changing it, `PageBlock.label` is typed as a required `never` in `packages/form-schema`, so `block.label` still types as `string`. At runtime `apps/api/src/ai/ai.service.ts` gets `undefined` for a page (for a paged form, that is every top-level block), with no compile error. Revisit when it comes back into scope: read names with `blockName`, then change `PageBlock.label` to `label?: never` so the compiler flags any remaining reads. (Phase 7, pages.)
- **The AI features know coded options only well enough to keep working.** Options are `{ code, label }` (contract §13). `apps/api/src/ai/ai.service.ts` still asks the model for plain option labels; each one becomes `{ code: "", label }` and the parse generates its code (§13.3). For "Ask AI" edits the model is shown the form with its codes but answers with labels, so every option it returns gets a code generated afresh from its label. An option the author had given its own code (or a renamed label) comes back with a different code, and conditions using the old code then fail the save check. Translate sends the whole schema to the model, codes included, and nothing stops it translating them. Revisit when AI features come back into scope: have the tools return `{ code, label }` and keep the existing codes. (Coded options.)
- **A code left invalid can lose track of its conditions.** When an option's code is changed, the conditions using it follow once the author leaves the field with a valid, unique code (contract §13.8). If the author leaves an invalid or clashing code, the editor remembers the code the conditions still use, by block, list and position (`codeOrigins` in `apps/web/src/components/form-editor/editor.tsx`), and they follow once it's fixed. Removing an option or importing into that block clears this memory, because positions shift. The conditions then stay on the old code. Nothing breaks silently: each one shows "the answer … isn't the code of any option" in its Logic section, and the save is refused until it's fixed. Revisit if authors hit it: give options a stable editor-only key instead of their position. (Coded options.)
- **The form editor isn't read-only for viewers.** A VIEWER can open any of the organisation's forms in the editor and change anything on the canvas and in the inspector — questions, logic, pages, settings, "Ask AI" — and the Save button is enabled. Only when they save does the API refuse, with 403 "Viewers have read-only access." (`assertCanEdit`), shown as "Couldn't save: …"; their edits stay on screen until they leave. The template actions are already hidden for viewers (the Team page's pattern: `useCanEdit`, write controls hidden rather than disabled), and a template opened by its address is read-only, but the form editor itself, "Generate with AI" on My forms and the form cards' menu (Duplicate, Delete) are not. Revisit: give the form editor a read-only mode for viewers (no Save or Cancel, inputs read-only, no insert menu or AI), and hide the other form write actions the same way. (Templates.)
- **The editor's existing dialogs don't return focus when they close.** The delete-group, delete-page and "Add pages" dialogs and the option import dialog move focus in when they open (`autoFocus`) and close on Escape, but when they close nothing puts focus back on the control that opened them, so a keyboard or screen reader user is left at the top of the page. Revisit: on close, put focus back on the control that opened each one, and check each with a screen reader. (Templates.)
