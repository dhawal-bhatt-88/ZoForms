## When you'd use this

<UseCases>
<UseCase title="Error reporting">
Send the form's failures to the same place as the rest of your app's.
</UseCase>
<UseCase title="Your own messages">
Show your own text after a failed submit, or take the respondent somewhere after a successful one.
</UseCase>
<UseCase title="Server responses">
Decide which faults are the request's and which are yours.
</UseCase>
</UseCases>

## Before you start

- A form rendered with `FormRenderer`. Each callback below is an optional prop.

## Steps

### 1. Know what can go wrong

| What went wrong | The respondent sees | Your app gets |
|---|---|---|
| The form can't be shown: a form file or a setting the renderer refuses, or a fault while rendering | "This form can't be shown right now. Please try again later." in its place. Your page stays up. | `onRenderError(error, { componentStack })`, once per failure |
| A submit failed | "Submission failed. Your answers have been kept — please try again.", with focus on it | `onError(error)` |
| Answers failed a check | A summary at the top, and a message on each question | Nothing: no request is sent |
| Progress couldn't be used, loaded, saved or deleted | Usually nothing, or a short notice | `onDraftProblem(problem)` |

### 2. Report a form that can't be shown

```jsx check=fragment
<FormRenderer
  schema={schema}
  endpoint="/api/submit"
  onRenderError={(error, { componentStack }) => report(error, componentStack)}
/>
```

- These errors don't reach an error boundary of yours. `onRenderError` is the way to hear about them.
- The message and `onRenderError` are the browser's. Where your server renders the page, as Next.js does, a form file the form refuses throws there instead. [Build an intake page in Next.js](/docs/integrate/tutorial-nextjs#5-put-the-form-in-a-client-component) shows what that does to a page.
- After a failure the form tries again when `schema` or `endpoint` changes. A form refused for its `validators`, which are often written inline and so new on every render, tries again when it gets a new React `key`.
- A form that can't be shown is often a newer `schemaVersion` than your package supports. The reason then says so: `This form uses schemaVersion 3, which this version of @zoworkhq/forms does not support (it supports 1 and 2). Upgrade @zoworkhq/forms to render it.`

### 3. Report a failed submit

```jsx check=fragment
<FormRenderer schema={schema} endpoint="/api/submit" onError={(error) => reportError(error)} />
```

`onError` is about submitting only. The error is one of:

- a response that isn't a 2xx, as an `Error` such as `Submission failed with status 500`;
- a network failure, from `fetch`;
- the time limit, `timeoutMs`;
- `getAuthHeaders` throwing or rejecting.

The form never reads the response body, so your endpoint's error message can't reach the respondent, or `onError`. [TODO: changing in 0.28.1]

### 4. Hear about progress that can't be kept

```jsx check=fragment
<FormRenderer
  schema={schema}
  endpoint="/api/submit"
  onDraftProblem={(problem) => console.warn('Drafts:', problem.type, problem.reason)}
/>
```

<FieldList of="DraftProblem">
<Field name="type">
What happened. `drafts-unavailable` means the form fell back to keeping progress in the tab only.
</Field>
<Field name="mode">
The mode the author chose: problems only come from device and server modes.
</Field>
<Field name="reason">
For `drafts-unavailable`, what was missing.
</Field>
<Field name="error">
The underlying error, when there is one.
</Field>
</FieldList>

A draft problem never blocks the form. With `drafts={{ mode: 'off' }}` there are no drafts, so there are no problems.

The respondent sees one of these notices, or nothing:

| When | Notice |
|---|---|
| A saved draft can't be decrypted or read | "Your saved draft couldn't be opened, so you're starting a new form." |
| The draft couldn't be loaded, or the key couldn't be got | "Your progress can't be saved for later on this visit." |
| The draft was saved on an older version of the form | "This form was updated since you saved your draft, so your earlier answers couldn't be kept." |
| A save on this device failed | "Your progress couldn't be saved just now. It will be saved again when you next change an answer." |
| A save to your server failed | "Your progress couldn't be saved just now. It will be saved again when you next move to another page." |

### 5. Answer your server's two kinds of fault

On your server, `prepareSubmission` **returns** `{ ok: false, errors }` for a bad request, and **throws** for a bad form file or a bad `validators` array. Answer the first with a 422, and let the second become a 500: no request can cause it, and it needs fixing in your code.

## What happens behind the scenes

- **Development builds say more.** The renderer checks `process.env.NODE_ENV`, which bundlers such as Vite and Next.js set. In a development build, "This form can't be shown" also shows the reason under it, and the console has warnings: a form file's media that will never show, a CSS reset that beats the stylesheet, and the same form mounted twice. A production build shows only the message.
- **Validators that fail are always logged.** In any build, the browser logs a validator that threw or returned a bad value with `console.error`, naming the field.
- **A failed submit keeps everything.** The answers, the page the respondent is on and the `idempotencyKey` all stay, so the next attempt is the same submission.

## Troubleshooting

**The message under "This form can't be shown right now." is missing.** That's a production build. Use `onRenderError` to see the reason.

**Your error boundary never sees the form's errors.** By design: the form shows its own message and calls `onRenderError`.

**`onError` fires but your server logged nothing.** The request never reached it: a network failure, the time limit, `getAuthHeaders`, or, on another origin, CORS. See [Send the submission with your app's sign-in](/docs/integrate/sign-in).
