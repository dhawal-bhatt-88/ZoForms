Executive Summary

What Tally is, why it works, and the thesis for building a better one.

Tally is a form builder that won by inverting the industry's rules. Where incumbents (Typeform, Jotform, Google Forms) meter responses and paywall the basics, Tally gives away unlimited forms and unlimited submissions for free, ships a Notion-like document editor that makes form-building feel effortless, and monetizes only the professional layer — branding removal, custom domains, teams, analytics, and data controls. Two founders bootstrapped it to roughly $5M ARR with a team of ~11, growing almost entirely through SEO and word-of-mouth. This document reverse-engineers how they did it and lays out a concrete blueprint to build a superior product.

The strategic wedge

A radically generous free tier removes the single biggest adoption barrier in the category — response caps — and turns every published form into an organic acquisition surface. The paywall sits on professionalization, not usage.

The product moat

The document-style editor with slash commands makes creation feel like writing, not configuring. Combined with beautiful defaults and a no-signup start, time-to-first-form is measured in seconds.

The growth engine

A library of SEO-optimized templates ranks in Google, embedded forms carry "Made with Tally" backlinks, and — remarkably — AI assistants became the #1 referral source. Near-zero paid CAC.

Where to beat them

Thin team/enterprise controls, minimal built-in AI, and shallow analytics are open flanks. A better product leads with AI-native creation and insight, deeper collaboration, and enterprise-grade governance — without sacrificing the generous-free ethos.

How to read this document

Conditional logic Free

Show/hide blocks based on prior answers. Rule-based (if answer = X then show Y). The workhorse of dynamic forms.

Branching / jump logic Free

Route respondents to different pages based on answers — skip irrelevant sections, build choose-your-path flows.

Calculations Free

Arithmetic over answers into calculated fields. Drives quiz scores, price quotes, and the amount charged by the Payment block.

Answer piping Free

Inject a previous answer into later question text or the Thank-You page (Hi @name), for conversational personalization.

The architecture splits cleanly into a read-heavy public plane (rendering and accepting form submissions at scale, must be cheap and cacheable) and a write-heavy authoring plane (the editor, dashboards, integrations, billing). We optimize each separately. Everything about Tally's actual stack is undocumented and labeled Assumption; everything about the product's observable behavior is Verified.

Multi-tenant model & data strategy

A single shared cluster (pooled multi-tenancy) — not a DB-per-tenant — keeps 500k+ teams economical on a bootstrapped cost base. Isolation is enforced in three layers:

  • Every domain row carries workspace_id; Prisma middleware injects the scope on every query.
  • Postgres Row-Level Security policies as a hard backstop against a missing app-layer filter.
  • Object-storage keys and search documents are namespaced by workspace; retention/purge jobs operate per-workspace.

The form schema is a versioned JSONB document (a block tree mirroring the TipTap model), which makes new block types additive with zero migrations and gives free Pro version history (store schema snapshots; 30/90-day windows Verified). Responses are stored schema-flexibly:

Philosophy: start lean, buy scale only when it bites

Tally reached ~$5M ARR with ~11 people (Verified). Copy that leverage. Each heavy component earns its way in only when a real metric forces it: move to K8s when PaaS bills/limits hurt; add ClickHouse when analytics event volume overwhelms Postgres; add a search cluster when Typesense stops keeping up. Premature infra is the tax that sinks small teams.

Contested tradeoffs, decided

FastAPI vs NestJS → NestJS

FastAPI is superb, but it forks the language — a Python API against a TypeScript editor kills the form-schema package that keeps client and server validation identical. NestJS keeps one language end-to-end, gives a small team guardrails (DI, modules, guards) as it grows, and can serve tRPC to the web app for zero-codegen type safety. We accept Python's ML edge is better and route AI work to jobs/services instead of the core API.

Redux vs Zustand → Zustand

The editor is a live document mutated dozens of times per second (drag, reorder, inline edit). Redux's action/reducer ceremony is friction at that cadence, and its serialize-everything default fights transient editor state. Zustand gives direct, minimal-boilerplate stores with selective subscriptions to avoid re-render storms. Server/cache state that Redux is often stretched to cover already lives in TanStack Query — so Redux would be redundant on both fronts.

MongoDB vs Postgres+JSONB → Postgres

The form schema and responses are semi-structured (JSONB fits), but teams, workspaces, RBAC, and billing are deeply relational and demand transactions and foreign keys. Postgres does both; a document DB would force a second store and lose integrity where money and access control live.

Elasticsearch vs Typesense → Typesense

Elastic's power comes with a heavy ops burden a lean team can't afford early. Typesense delivers typo-tolerant, sub-50ms search for templates and responses with a fraction of the operational surface. Revisit Elastic/OpenSearch only if search needs outgrow it.

11.3 Form-schema storage strategy

We store the entire form structure as a versioned JSONB document (form_versions.schema), not a fully-normalized form_blocks table. The editor is a Notion-like document Verified, so blocks are inherently an ordered, heterogeneous tree — a natural JSON shape. Publishing writes a new immutable form_versions row; forms.published_version_id points to the live one. This gives version history 30-day 90-day for free.

Versioned JSONB (chosen)

Whole-form read/write in one row; trivial snapshots & rollback; schema evolves without migrations; matches editor's block model 1:1; responses can reference the exact version they answered. Cost: no cross-form column queries on individual questions without a projection.

Fully-normalized blocks (rejected)

A form_blocks table per question enables SQL over question metadata, but forces N-row rewrites on every edit, painful ordering/reparenting, migration churn as block types grow, and expensive version snapshots. Overkill for a document editor.

Responses store a JSONB answers object keyed by block_id, plus the version integer so we can always interpret an answer against the schema it was submitted against — critical because forms mutate. A GIN index (jsonb_path_ops) supports filtered queries; a nightly job can materialize a flattened response_answers projection for CSV export and column analytics without paying normalization cost on the write path.

11.5 Multi-tenancy, indexing, partitioning & retention

Multi-tenancy

org_id on every tenant-owned table (denormalized onto form_versions, responses, audit_logs to avoid joins for scoping). Enforce Postgres Row-Level Security with a SET app.current_org session GUC as defense-in-depth; the NestJS repository layer always injects org_id so a query can never leak across tenants even if RLS is off.

Indexing

Composite leading-org_id/form_id B-trees for list views; GIN jsonb_path_ops on answers for filter queries; partial indexes (WHERE deleted_at IS NULL) to keep hot indexes small; pg_trgm on forms.title for in-app search (Typesense/Meilisearch for cross-form response search).

Partitioning

responses is RANGE-partitioned by submitted_at (monthly), auto-provisioned by pg_partman via a BullMQ cron. With unlimited submissions Verified this is essential: queries prune to a few partitions, retention becomes an O(1) DROP TABLE, and index bloat stays bounded. High-traffic forms can be sub-partitioned by form_id hash.

Retention & soft-delete

deleted_at soft-delete on user-facing entities (trash/restore UX). Data-retention auto-delete Business is a per-form settings.retention_days; a nightly worker hard-deletes expired responses + their S3 files and drops empty partitions. Audit logs are append-only and exempt.

Why the public submit endpoint is hardened by construction

It is the one route an attacker can hit at will. Four layers protect it: (1) a per-form submission token from /session binds the submit to a real page load; (2) reCAPTCHA + honeypot + Cloudflare bot score gate obvious bots (reCAPTCHA is Verified available); (3) an idempotency key (client-generated UUID) makes double-taps and retries safe — the second POST returns the first result, never a duplicate row (aligns with the Verified "prevent duplicate submissions" feature); (4) per-IP + per-form rate limits in Redis. Validation is re-run server-side against the published schema with Zod — the client bundle is never trusted.

13.5 Deployment, migrations & rollback

Release strategy

Containerised (Docker). Fly.io/Render early stage using built-in blue-green; migrate to Kubernetes at scale with Argo Rollouts for canary (5% → 25% → 100%, gated on error-rate + latency SLO). Workers deploy as a separate deployment from the API.

Migrations: expand/contract

Schema changes ship backward-compatible first. Expand: add nullable column / new table, deploy code that writes both. Migrate: backfill via job. Contract: a later release drops the old column once no code reads it. Never a breaking DDL in the same deploy as the code that needs it.

Rollback

App rollback = repoint blue-green / re-promote previous image (seconds), safe because expand/contract kept the old schema readable. Data rollback avoided by design; forward-fix migrations preferred over down migrations in prod.

The rule that prevents 2am incidents

A deploy and the migration it depends on are decoupled. Because every migration is additive until the contract phase, the previous app image always runs against the new schema. That is what makes instant blue-green rollback actually safe — the usual killer is "rolled back the code but the DB already changed."

Security & Compliance

A form builder is a hostile-input machine: it accepts untrusted rich content from creators and untrusted submissions from the anonymous public, then fans that data out to webhooks and integrations — so security is a product feature, not a checkbox.

Threat model in one paragraph

Two adversarial surfaces dominate. (1) The form editor lets tenants inject rich HTML/embeds that later render in a victim's browser — a stored-XSS vector against form respondents and against other workspace members. (2) The public submit endpoint is unauthenticated, high-volume, and a magnet for spam bots, credential-stuffing of email fields, and resource-exhaustion abuse. Everything below is engineered around isolating these two surfaces while keeping a legitimate anonymous respondent's path frictionless.

1. Authentication

Tally's own auth is Assumption (undocumented). We prescribe a session + JWT hybrid on the canonical stack: a long-lived, HttpOnly, Secure, SameSite=Lax session cookie for first-party web app calls, and short-lived (10–15 min) access JWTs minted from that session for the NestJS API and embed runtime, with rotating refresh tokens stored server-side in Redis so sessions are revocable.

Passwords & passwordless

Argon2id hashing (memory-hard), per-user salt, breach-check against HaveIBeenPwned k-anonymity API on set. Offer magic-link + OAuth (Google, Microsoft, Apple) to reduce password surface entirely for the mass market.

MFA / TOTP

RFC 6238 TOTP (authenticator apps) + WebAuthn/passkeys as the strong second factor. Recovery codes issued once, hashed at rest. MFA enforceable per-workspace by admins (a Business/Enterprise policy toggle).

Enterprise SSO

SAML 2.0 + OIDC via WorkOS, plus SCIM 2.0 for automated user provisioning/de-provisioning. De-provisioning on SCIM active:false immediately revokes sessions — a hard requirement for enterprise deals and a gap Tally has no public answer for.

SSO + SCIM is the clearest wedge for an upmarket Enterprise tier: Tally lists no Enterprise plan, so no advertised SAML/SCIM. Assumption

Authorization is enforced server-side on every row. We never trust a client-supplied workspaceId; the tenant scope is derived from the authenticated principal and injected into every Prisma query. 4. Encryption & secrets management

In transit

TLS 1.2+ everywhere (prefer 1.3), HSTS with preload, TLS terminated at Cloudflare and re-encrypted to origin (full-strict). SSL-for-SaaS issues per-tenant certs for custom domains. Encrypted (marketing claim)

At rest

Scalability — 100 to 1M Users

A staged evolution of the recommended stack, tuned to the real bottlenecks of a form product and disciplined about deferring cost until traffic demands it.

A form product has a lopsided traffic shape: a small number of authenticated builders editing forms, and a very large, spiky, unauthenticated respondent population hitting published forms and writing submissions. The five bottlenecks specific to a form product

1. Response write throughput

Submissions are the critical write. Keep the synchronous path tiny: validate (Zod), INSERT the response as JSONB, enqueue everything else, return 200. Partition responses by month (and/or by form) so writes hit small, hot partitions and vacuum stays cheap. Use PgBouncer transaction pooling so thousands of ephemeral respondent connections don't exhaust Postgres. Never run integrations inline.

2. Analytics event volume

Form-visit, view, field-focus, and drop-off events outnumber submissions 50–100×. Writing them to Postgres poisons the primary. Batch them client-side, ship to an ingest endpoint, buffer in Redis/Kafka, and land them in ClickHouse (Stage 3+). Funnel/drop-off queries then run on a columnar store built for it, not on your OLTP DB.

3. Webhook & integration fan-out

One submission may trigger Google Sheets, Slack, a webhook, and an email — each slow, each able to fail. All go through BullMQ with per-endpoint concurrency caps, exponential-backoff retries, and a dead-letter queue. Fan-out is decoupled from ingest so a slow customer endpoint never delays the respondent's confirmation.

4. File storage growth

Uploads grow monotonically and unboundedly. Presigned direct-to-R2/S3 uploads keep bytes off the app tier entirely. Enforce per-plan caps (10MB free, unlimited Pro Pro), lifecycle rules for cold data, and honor Business data-retention auto-delete Business. Egress is metered and cached at the CDN.

5. Public-form render latency

A published form is effectively static until edited. Serve its schema JSON from the CDN edge (Cloudflare KV / cache), keyed by form id + version; publishing purges that key. The runtime is a tiny standalone bundle (React Hook Form + Zod). The respondent never touches Postgres to view a form — only to submit.

Cross-cutting: horizontal API scale

Keep the API fully stateless (sessions in Redis, nothing on local disk) so replicas scale linearly behind the load balancer. Split the form-runtime service (public, spiky, cache-heavy) from the editor/dashboard service (authenticated, write-heavy) so a viral form can't starve builders.

Premature optimization — what NOT to build until you need it

Every item below is a real cost that buys nothing at Stage 1–2 and slows you down. Defer ruthlessly:

  • Kubernetes before ~10k users — Fly.io/Render autoscaling is plenty; K8s is a full-time job you don't have.
  • Microservices from day one — ship the modular monolith; split only the form-runtime service when its traffic shape actually diverges.
  • Database sharding before a single primary + replicas is measurably saturated — sharding is a one-way door that complicates every query.
  • ClickHouse / Kafka before analytics volume actually hurts Postgres — a partitioned Postgres table serves early analytics fine.
  • Multi-region before you have paying customers demanding it — it multiplies infra, data-consistency, and on-call burden.
  • A dedicated search cluster when Postgres trigram/ILIKE answers template and response search at low volume.
  • Custom autoscalers, service mesh, self-hosted everything — managed Postgres, managed Redis, and Cloudflare buy you years of runway.

The bootstrapped lesson from Tally itself Assumption: an ~11-person team reached ~$5M ARR — small teams win by not operating infrastructure they don't yet need. The one rule that scales the whole product

Keep the synchronous submit path down to validate → write → enqueue → respond, and serve the published form from the edge. Get those two right and the same architecture carries you from 100 to 1M users with mostly additive changes — no rewrites.

Capacity Planning & Scaling Design

How many users and responses each infrastructure tier can actually carry — and the scale-out design that lets capacity grow layer by layer.

How to read these capacity numbers Assumption

Throughput figures are engineering estimates for a well-tuned stack (indexed Postgres, connection pooling, edge caching, async writes). Real ceilings vary with query shape, payload size, and traffic burstiness by ±40%. They are meant for sizing decisions, not guarantees — always load-test before a launch. Each tier maps 1:1 to the cost phases in the previous section.

The capacity model — what actually creates load

A form product has two very different traffic types, and conflating them is the #1 capacity-planning mistake:

Respondent traffic (public, high volume)

Form render (GET) — cacheable at the edge, so it scales almost for free via CloudFront. Submission (POST) — a write; the real limiter, but absorbed by a queue so origins rarely feel spikes.

Creator traffic (authenticated, low volume / heavy)

Builder autosaves, dashboards, browsing responses, analytics. Far fewer requests, but heavier queries — served off read replicas so they never contend with submissions.

From "responses/month" to peak load (the math)

Average submits/sec = monthly ÷ 2,592,000. But traffic concentrates — peaks run ~15–30× the average (business hours, campaigns, virality). So a form doing 1M responses/month averages only ~0.4 submits/sec, but you design for ~8–12/sec peak. Views run 5–20× submissions on top of that — but they are edge-cached. Net: because reads cache and writes queue, the origin database is asked to do far less than the headline numbers suggest.

What breaks first — and what you scale

Capacity is a sequence of moving bottlenecks. The design goal is that each ceiling has a pre-planned, mostly-horizontal fix, so no single rewrite is ever forced:

~50k users — DB writes/connections tighten → add pgBouncer, a read replica for dashboards, and CloudFront to cache form renders.
~500k users — reads and spikes dominate → queue-buffer submissions (SQS), add Aurora readers, move analytics off the OLTP path.
~5M+ responses/table — indexes slow → partition the responses table by month/form; push events to ClickHouse.
Single-region write ceiling — shard by workspace and/or go multi-region active-active.

Scale-out design principles (built in from day one)

  • Stateless app tier behind an ALB — add instances for linear capacity; no sticky sessions.
  • Edge-cache the published form (CloudFront) — respondent reads scale globally, decoupled from the origin.
  • Queue-buffer submissions (SQS / BullMQ) — absorb 20× spikes, protect the DB, retry safely; return a fast 202.
  • Read replicas for dashboards & exports — heavy reads never touch the write primary.
  • Partition the responses table by time/form — keep inserts and indexes fast as rows reach the hundreds of millions.
  • Separate analytics store (ClickHouse) — reporting queries never contend with live submissions.
  • Async webhook & integration fan-out via workers — a slow downstream never blocks a submit.
  • Autoscaling policies on CPU, p95 latency, and queue depth — capacity follows demand automatically.
  • Multi-AZ everywhere; shard-by-workspace / multi-region only at the very top end.

What to cut from MVP to ship fast

Cut ruthlessly. None of these block the core build–publish–collect loop, and each can ship later without re-architecture:

  • Advanced/rare blocks — ranking, matrix, linear scale, signature, calculated fields. Ship the 10 common inputs; add the rest in V2.
  • All integrations except Google Sheets + webhook. Notion/Airtable/Slack/Zapier all wait for V2 — a webhook covers power users on day one.
  • Analytics, version history, partial submissions, custom domains — these are Pro-tier retention features, not acquisition features. V2.
  • Advanced customization + custom CSS, custom email domains — polish, not core. Ship one clean default theme.
  • Popover / side-tab / full-page embeds — inline + popup cover 90% of use; add the rest later Embed types verified.
  • All of AI. Tempting, but it is a Phase-3 moat, not a launch requirement. Do not let it delay the loop.

What you must not cut: the Notion-like editor feel, conditional logic, no-signup-to-start, and SEO-rendered template pages. These are the four things that made Tally win.
